A production MCP server answers 401 to anyone without a credential. Give
mcpscore the same credential your MCP client uses and it audits everything
behind the gate.

```bash
# Audit GitHub's MCP server with your GitHub CLI token
MCPSCORE_TOKEN="$(gh auth token)" mcpscore https://api.githubcopilot.com/mcp/
```

```text
Using 1 custom header(s).
Attempting Streamable HTTP connection...
Connected to the MCP server: https://api.githubcopilot.com/mcp/
...
Audit finished. Final score: 202/218
Spec: 2025-11-25 negotiated (latest: 2026-07-28) · era: dual-era
```

That is a full audit: every rule ran against the live session. The token
is sent as an `Authorization` header and is never logged or written to the
report.

## Step 1: see what a stranger sees

Start without a credential. mcpscore detects the 401 and scores the part
of the server that an anonymous client can observe.

```bash
mcpscore https://api.githubcopilot.com/mcp/
```

```text
✅ Server uses HTTPS with valid TLS (TLSv1.3).
✅ The observed HTTP 401 response carries a non-empty WWW-Authenticate challenge.
✅ Protected resource metadata identifies "https://api.githubcopilot.com/mcp".
✅ All 1 authorization server(s) use HTTPS.
...
❌ The authorization server does not advertise PKCE with S256 (code_challenge_methods_supported).
...
⚠️  Partial audit (Server requires authentication (HTTP 401); scored the unauthenticated surface only — pass a token to audit behind the gate.).
Only the auth, TLS, and transport surface was scored — not comparable to a full audit.
Audit finished. PARTIAL score: 24/27 from 10 of 79 checks — not comparable to a full audit.
```

This is a partial audit. It covers TLS, the 401 challenge, the
[RFC 9728](https://www.rfc-editor.org/rfc/rfc9728) protected-resource metadata, and the authorization server that metadata
names. Those are real findings about your auth posture, and a missing PKCE
advertisement shows up here without any credential.

The score line says `PARTIAL` and `from 10 of 79 checks` on purpose. A
bare `24/27` reads as a near-perfect result when pasted into a chat. A
partial score and a full score are not comparable.

A partial audit cannot pass a threshold. Add `--fail-under` and it fails:

```bash highlight={1}
mcpscore https://api.githubcopilot.com/mcp/ --fail-under 80
echo $?
```

```text
Gate failed — --fail-under 80: this was a partial audit — its score covers only the observable surface and cannot demonstrate the threshold; pass a credential to audit behind the gate (or drop --fail-under for partial audits)
3
```

## Step 2: pass a token

Add `--token`. It is shorthand for
`--header 'Authorization: Bearer <token>'`.

```bash highlight={1}
mcpscore https://api.githubcopilot.com/mcp/ --token "$(gh auth token)"
```

```text
Using 1 custom header(s).
...
Audit finished. Final score: 202/218
```

The `PARTIAL` marker is gone and the check count is back to the full rule
set. In the JSON report, `authenticated` is `true` and `partial` is
`false`.

## Step 3: keep the token out of your shell history

A value passed to `--token` lands in your shell history and in the process
list. Set `MCPSCORE_TOKEN` instead. mcpscore reads it whenever `--token` is
absent.

```bash highlight={1}
export MCPSCORE_TOKEN="$(gh auth token)"
mcpscore https://api.githubcopilot.com/mcp/
```

The output is identical to step 2. This is the form to use in CI, where the
token comes from a secret.

## Step 4: send an API key or any other header

Servers that authenticate with an API key take `--header`, which works the
same way as `--token` and repeats:

```bash highlight={2-3}
mcpscore https://your-server.example/mcp \
  --header "X-Api-Key: $API_KEY" \
  --header 'X-Tenant: acme'
```

```text
Using 2 custom header(s).
...
```

Only an `Authorization` header sets `authenticated: true` in the report.
Other headers are sent on every request, but the report makes no claim
that the audit ran behind the gate. An explicit `Authorization` header wins
over `--token` and `MCPSCORE_TOKEN`.

## Step 5: sign in through the browser with OAuth

When you have no token to paste, `--oauth` gets one. It opens your browser
on the server's own sign-in page, runs the authorization code flow with
PKCE, and holds the token in memory for this one audit.

```bash highlight={1}
mcpscore https://your-server.example/mcp --oauth
```

```text
OAuth flow completed — token held in memory only for this audit.
...
Audit finished. Final score: ...
```

`--oauth` registers mcpscore as a client on the fly (dynamic client
registration, [RFC 7591](https://www.rfc-editor.org/rfc/rfc7591)). Some authorization servers, GitHub's among them,
do not offer registration. For those, register an OAuth app once and pass
its client ID:

```bash highlight={1}
mcpscore https://api.githubcopilot.com/mcp/ --oauth --client-id "$OAUTH_CLIENT_ID"
```

The registered app must allow the loopback redirect
`http://127.0.0.1:<port>/callback`. If the authorization server insists on
the exact registered port, pin it with `--callback-port`.

<Accordion title="Technical details">
- The flow follows the [MCP authorization spec](https://modelcontextprotocol.io/specification/draft/basic/authorization):
  mcpscore reads the server's protected-resource metadata, discovers the
  authorization server, and runs the authorization code grant with PKCE.
- The token is never written to disk and never logged. It is placed in the
  `Authorization` header for the audit and discarded when the process exits.
- `--oauth` refuses to run alongside `--token`, an `Authorization`
  `--header`, or `MCPSCORE_TOKEN`, so the server never receives two
  credentials.
- [RFC 8252 §7.3](https://www.rfc-editor.org/rfc/rfc8252#section-7.3)
  requires authorization servers to accept any port on a loopback
  redirect. `--callback-port` exists for the servers that do not follow it.
</Accordion>

## Use it in CI

Store the token as a repository secret and expose it as `MCPSCORE_TOKEN`.
Nothing else changes. With the [GitHub Action](/github-action):

```yaml highlight={4-6}
- uses: mcp-box/mcpscore-action@v1
  with:
    target: https://your-server.example/mcp
    args: --fail-under 80
  env:
    MCPSCORE_TOKEN: ${{ secrets.MCPSCORE_TOKEN }}
```

Gate a server behind auth with `--fail-under` in `args`, as shown. If the
secret is missing or expired, the run becomes a partial audit and
`--fail-under` fails the job with exit `3`. The Action's `min-score` input
compares the percentage only, so a partial `24/27` passes it at 89%.

## Options

| Flag | Default | What it does |
|---|---|---|
| `--token TOKEN` | `MCPSCORE_TOKEN` | Sends `Authorization: Bearer TOKEN`. |
| `--header 'Name: Value'` | none | Sends any header. Repeatable. Wins over `--token` for `Authorization`. |
| `--oauth` | off | Gets a token through the browser OAuth flow. HTTP(S) targets only. |
| `--client-id ID` | none | Pre-registered OAuth client, for servers without dynamic registration. Needs `--oauth`. |
| `--callback-port PORT` | any free port | Fixed loopback port for the OAuth redirect. Needs `--oauth`. |

| Report field | Meaning |
|---|---|
| `authenticated` | `true` when the audit sent a non-blank `Authorization` credential. |
| `partial` | `true` when only the unauthenticated surface was scored. |
| `partial_reason` | Why the audit is partial, in the same words as the terminal output. |

## When it fails

**`Partial audit (Server rejected the provided credentials (HTTP 401) ...)`**

- Cause: the server refused the token you sent.
- Fix: check the token is current and has access to this server. For
  GitHub, `gh auth status` shows the account and scopes.

**`Partial audit (... the session could not be established (HTTP 400), so the supplied credentials were never exercised ...)`**

- Cause: the connection failed before the credential was used. The server
  answered the session request with an error that is not an auth refusal.
- Fix: check the token's format against what the server expects. An
  invalid GitHub token produces this exact message.

**`PARTIAL score` although you passed `--header`**

- Cause: the header was not `Authorization`, so the server still answered
  401 to mcpscore's session.
- Fix: send the credential in the header the server checks. If the server
  expects a bearer token, use `--token`.

**`Gate failed — --fail-under 80: this was a partial audit`** (exit `3`)

- Cause: no credential reached the server, so the score cannot demonstrate
  the threshold.
- Fix: pass a credential, or drop `--fail-under` for that run.

**`OAuth: OAuth flow failed: ... try --client-id`** (exit `1`)

- Cause: the authorization server does not support dynamic client
  registration.
- Fix: register an OAuth app yourself and pass `--client-id`.

**The browser shows a redirect URI mismatch**

- Cause: the authorization server requires the exact registered redirect,
  port included.
- Fix: pin the registered port with `--callback-port`.

## Recap

- Run without a credential to see the partial audit of your auth posture.
- Pass `--token` to audit behind the gate.
- Move the token to `MCPSCORE_TOKEN` to keep it out of shell history.
- Send API keys with `--header`.
- Use `--oauth`, with `--client-id` if needed, when you have no token.
- In CI, set `MCPSCORE_TOKEN` from a secret and gate with `--fail-under`.
