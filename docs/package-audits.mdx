Before anyone runs your server, they find it on a registry. A listing that
doesn't resolve, hides its license, or links no source loses them before the
first `npx`. `--package` scores that listing from registry metadata alone.

```bash
# Latest release on npm
mcpscore --package npm:@modelcontextprotocol/server-everything

# A specific release on PyPI
mcpscore --package pypi:mcp-server-fetch==2025.4.7

# Same JSON report shape as a server audit
mcpscore --package pypi:your-server --json > report.json
```

```text
📦 Auditing package npm:@modelcontextprotocol/server-everything
Resolved version: 2026.8.31
✅ Package '@modelcontextprotocol/server-everything' is published on npm
✅ No version pinned; the registry's latest is '2026.8.31'
✅ Release '2026.8.31' is not withdrawn
✅ Source repository declared: https://github.com/modelcontextprotocol/servers
✅ License declared: SEE LICENSE IN LICENSE
✅ Description present: 'MCP server that exercises all the features of the MCP protocol'

Audit finished. Final score: 16/16
Packaging audit of npm:@modelcontextprotocol/server-everything — metadata only, the package was not downloaded or run.
```

The package is never downloaded and never executed, so no install hook runs.
The report's `package.executed` field records that and is always `false`.

## What it checks

The six packaging rules, in the order the output prints them: the coordinate
resolves on its registry, the pinned version exists, the release is not
withdrawn or yanked, and a source repository, a license, and a description are
declared. Weights and severities are in the
[rules reference](/rules#packaging-rules).

## Two questions, two scores

A package audit answers *is this server well published?* A server audit
answers *does it speak MCP?* The two rule sets are disjoint, so their scores
share no denominator and are never comparable. In the JSON report a non-null
`package` object is the marker that a report is a package audit. Anything that
aggregates scores must branch on it.

To answer the second question, run the package through its own runner:

```bash
mcpscore --stdio npx -y @modelcontextprotocol/server-everything
mcpscore --stdio uvx mcp-server-fetch
```

## When it fails

**`❌ No package '@scope/name' published on npm`, then `Final score: 0/5`**

- Cause: the name does not exist on that registry, so the other five rules
  have nothing to read and skip.
- Fix: check the coordinate. Scoped npm packages keep their `@`:
  `npm:@scope/name`. PyPI pins use `==`: `pypi:name==1.2.3`.

**`Could not read npm metadata: ...`** (exit `2`)

- Cause: the registry itself was unreachable.
- Fix: retry once the network is back. Nothing about the package is scored
  until the registry answers.

**`Package - Pinned version resolves` fails**

- Cause: the version you pinned was never published, or was removed.
- Fix: drop the pin to audit the latest release, or pin one that exists.
