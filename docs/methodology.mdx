A score you cannot check is a score you cannot trust. This page is the whole
method: how the number is computed, what runs against your server, what is
deliberately left out, and how to dispute a rule. Every claim here is one you
can verify from the JSON report and the spec.

## Four principles

| Principle | What it means for you |
|---|---|
| **Deterministic** | No LLM judging, no API keys, no sampling. The same server state always produces the same score, in seconds, so the score works as a CI gate |
| **Spec-anchored** | Every rule enforces something the [MCP specification](https://modelcontextprotocol.io/specification) or its published best practices say, and the citation ships in every result: `details.basis` for most rules, `details.sep` for readiness rules |
| **Fair across revisions** | Servers are scored against the revision they negotiated, never punished for a spec they don't speak yet |
| **Honest about limits** | Anything mcpscore cannot verify from the outside is [listed as untested](#what-mcpscore-does-not-test), not silently skipped |

## The score

Each rule has a severity. A passing rule adds its weight. The score is
`earned/maximum`.

| Severity | Weight | Meaning |
|---|---|---|
| CRITICAL | 5 | Spec violations that break interoperability: protocol version, server name, TLS |
| HIGH | 3 | Strong spec expectations: server version, valid tool schemas |
| MEDIUM | 2 | Recommendations that improve agent UX: titles, descriptions, error hygiene |
| LOW | 1 | Nice-to-haves: capability extras, transport recommendations |

Only applicable rules count toward the maximum. A rule that cannot
meaningfully run is skipped and excluded from both numbers, never failed.
Every skip appears in the report's `skipped_rules` with one of three reasons:

| Skip reason | When |
|---|---|
| `not-applicable` | The rule has no subject: its requirement does not exist for the negotiated version or transport, or an optional catalog has no items to judge |
| `insufficient-data` | The observations the rule needs are unavailable, for example a probe errored. The rule can neither pass nor fail |
| `requires-modern-support` | A readiness detail check on a server with no modern-lifecycle support. The gateway rules already carry that verdict |

An empty tools catalog that was fetched successfully gives the per-tool rules
nothing to assess, so they contribute `0/0` as `not-applicable`. A declared
catalog that could not be fetched uses `insufficient-data` instead, because an
item may exist unobserved. A separate presence rule still judges whether a
complete catalog is empty.

## How an audit runs

<Steps>
  <Step title="Connect">
    Stdio for local servers, Streamable HTTP or SSE for URLs, detected
    automatically. mcpscore tries the legacy `initialize` handshake first. If
    that lifecycle is absent, stateless probes establish whether the target is
    a modern-only server rather than an unreachable one.
  </Step>
  <Step title="Collect">
    Protocol version, server info, capabilities, and the complete paginated
    listings of tools, prompts, resources, and resource templates, plus TLS
    details for HTTPS targets.
  </Step>
  <Step title="Probe">
    Sessionless requests that observe behavior the spec defines outside the
    negotiated session. Probes read state and nothing more. **An audit never
    invokes `tools/call`.** The one opt-in exception is the CLI's
    [smoke mode](/smoke-mode), for your own server, reported outside the score.
  </Step>
  <Step title="Evaluate">
    Every registered rule runs against the collected data and probe
    observations. The [rules reference](/rules) lists them all.
  </Step>
</Steps>

### What the probes send

Several probes are deliberately malformed, because the spec says how a server
must answer them. They can look like scanning in a WAF log. Each one checks
documented normative behavior:

| Probe | What the spec requires |
|---|---|
| A foreign `Origin` header | HTTP 403 |
| An unknown RPC method | HTTP 404 with JSON-RPC `-32601` |
| An unsupported protocol version | Rejection naming the supported versions |
| A bogus session ID | Rejection, not a fresh session |
| A request for a nonexistent resource | The standard `-32602` |
| A fabricated pagination cursor on each declared list | JSON-RPC `-32602` (recommended) |
| One truncated JSON body | JSON-RPC `-32700` with a null ID |

A few probe details matter when reading a report:

- **Stdio gets the same JSON-RPC probes.** The modern lifecycle is stateless,
  so behaviors expressible through the SDK are probed over stdio too, using
  two short-lived sibling processes and no `initialize` handshake. The
  truncated-JSON probe runs only over HTTP, because the SDK path cannot
  inject malformed wire input safely, so stdio reports `insufficient-data`
  for that rule. HTTP-only questions such as `Origin`, headers, status codes,
  sessions, and auth metadata are `not-applicable` for stdio, never failed.
- **Invalid-cursor probes use the initialized session** when one exists.
  Legacy and dual-era servers may reject a sessionless request before the
  cursor can be judged. Modern-only servers are assessed through the
  stateless path.
- **Pagination traversal is bounded.** For modern servers, mcpscore follows
  declared paginated lists to compare `cacheScope` across pages. It is
  read-only, capped at 100 pages per surface and 30 seconds in total, and
  skips when no list returns multiple complete pages.

## Scoring across spec revisions

MCP publishes dated revisions, `2024-11-05` through `2026-07-28`. The 2026
revision replaces the stateful `initialize` lifecycle with a stateless one,
and the spec itself describes servers as **legacy** (stateful), **modern**
(stateless), or **dual-era** (both). mcpscore treats the revision as a
property of your server that it detects, not a mode of the tool:

- Rules declare the version range they apply to. Outside it they are skipped,
  which keeps scores comparable across servers on different revisions.
- The report's `spec.era` states which lifecycle was observed, following the
  spec's own detection guidance.
- Modern-only servers are fully supported over HTTP and stdio. If the legacy
  handshake fails but stateless requests succeed, the audit runs through the
  probe layer instead of reporting a connection failure.

## The readiness axis

mcpscore answers a second question: is this server ready for the 2026-07-28
revision? The answer is always its own axis, `readiness.score` over
`readiness.max_score`, and how it relates to the main score depends on the
server:

| Server | Readiness points | Report flag |
|---|---|---|
| Legacy only | Informative. Guidance, not punishment. A fully compliant 2025-11-25 server keeps a clean main score | `readiness.counted_in_main: false` |
| Modern or dual-era | Counted in the main score as well. The readiness block stays as the transparent breakdown of that share | `readiness.counted_in_main: true` |
| Partial audit | Never counted. A partial score is already not comparable | `readiness.counted_in_main: false` |

Whenever any readiness check was skipped, the human-readable line says how
many were assessed, and the report carries `readiness.assessed`,
`readiness.skipped`, and `readiness.total`. A perfect fraction never implies
that every check ran.

Each readiness rule is anchored to normative language of the 2026-07-28
revision. The citations were re-verified against the dated spec URLs the day
the revision went final, and are re-checked whenever a revision does.

| Rule | Severity | Normative basis |
|---|---|---|
| `readiness_2026_server_discover` | CRITICAL | Servers MUST implement `server/discover` ([SEP-2575](https://modelcontextprotocol.io/specification/2026-07-28/changelog)) |
| `readiness_2026_stateless_request` | CRITICAL | Requests carry their context in `_meta`; the `initialize` handshake is removed ([SEP-2575](https://modelcontextprotocol.io/specification/2026-07-28/changelog)) |
| `readiness_2026_supported_versions` | HIGH | `server/discover` MUST list at least one supported version ([SEP-2575](https://modelcontextprotocol.io/specification/2026-07-28/changelog)) |
| `readiness_2026_origin_validation` | HIGH | An invalid `Origin` MUST be rejected with HTTP 403 ([Streamable HTTP](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http#security-&-endpoint)) |
| `readiness_2026_unknown_method_error` | HIGH | Unimplemented methods MUST return HTTP 404 with `-32601` ([Streamable HTTP](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http#protocol-version-header)) |
| `readiness_2026_response_content_type` | HIGH | Successful responses MUST be `application/json` or `text/event-stream` ([Streamable HTTP](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http#sending-messages)) |
| `readiness_2026_meta_validation` | HIGH | Requests missing required `_meta` fields MUST be rejected with `-32602` + HTTP 400 |
| `readiness_2026_header_validation` | HIGH | Header/body mismatches MUST be rejected with `-32020` (HeaderMismatch) + HTTP 400 ([SEP-2243](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http)) |
| `readiness_2026_cache_metadata` | HIGH | List/discover results MUST carry `ttlMs >= 0` and `cacheScope` ([SEP-2549](https://modelcontextprotocol.io/specification/2026-07-28/server/utilities/caching)) |
| `readiness_2026_no_session_id` | HIGH | No `Mcp-Session-Id` minted or echoed on modern requests ([SEP-2567](https://modelcontextprotocol.io/specification/2026-07-28/changelog)) |
| `readiness_2026_unsupported_version_error` | MEDIUM | Unknown protocol versions MUST be rejected with `-32022` naming the supported versions |
| `readiness_2026_error_code_migration` | MEDIUM | Missing resources yield `-32602`; the legacy `-32002` MUST NOT be emitted ([SEP-2164](https://modelcontextprotocol.io/specification/2026-07-28/changelog)) |
| `readiness_2026_result_type` | MEDIUM | All results carry the `resultType` discriminator ([SEP-2322](https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/mrtr)) |
| `readiness_2026_deprecated_features` | MEDIUM | Features deprecated in 2026-07-28 (logging; SHOULD NOT adopt) ([SEP-2577](https://modelcontextprotocol.io/specification/2026-07-28/deprecated)) |
| `readiness_2026_removed_methods` | MEDIUM | Removed methods such as `ping` rejected with 404 + `-32601`, not served ([SEP-2575](https://modelcontextprotocol.io/specification/2026-07-28/changelog)) |
| `readiness_2026_no_get_stream` | MEDIUM | Modern-only endpoints SHOULD reject the removed standalone GET stream with HTTP 405 ([Streamable HTTP](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http#earlier-streamable-http-revisions)) |
| `readiness_2026_missing_protocol_version_rejected` | LOW | Modern-only endpoints MUST reject a missing `MCP-Protocol-Version` with `-32020` + HTTP 400 ([Streamable HTTP](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http#server-validation)) |
| `readiness_2026_missing_method_header_rejected` | LOW | A missing `Mcp-Method` MUST be rejected with `-32020` + HTTP 400 ([Streamable HTTP](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http#server-validation)) |
| `readiness_2026_resource_name_header_mismatch_rejected` | LOW | A `resources/read` `Mcp-Name` that contradicts `params.uri` MUST be rejected with `-32020` + HTTP 400 ([Streamable HTTP](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http#server-validation)) |
| `readiness_2026_prompt_name_header_mismatch_rejected` | LOW | A `prompts/get` `Mcp-Name` that contradicts `params.name` MUST be rejected with `-32020` + HTTP 400 ([Streamable HTTP](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http#server-validation)) |
| `readiness_2026_tool_schema_dialect` | LOW | Tool schemas valid under the default JSON Schema 2020-12 dialect; no network-URI `$ref` ([SEP-2106](https://modelcontextprotocol.io/specification/2026-07-28/basic/index)) |

The session-ID and removed-method rules are legacy-leakage checks and run
only when the server shows modern support. Missing-protocol-version rejection
and GET-stream removal skip dual-era endpoints, because the spec explicitly
permits compatibility with older Streamable HTTP revisions.

## What mcpscore does not test

Out of scope today, either because it is not observable from outside or
because testing it safely from outside is not yet possible:

- **True statelessness**, meaning no hidden cross-request state. Only
  probabilistically testable, as the spec itself concedes.
- **`requestState` integrity enforcement** (MRTR). Only tamper rejection is
  observable, and active tampering probes are deferred.
- **`subscriptions/listen`** behavior and SSE stream semantics.
- **Tasks and MCP Apps extensions**, which version independently of the core.
- **Client-side OAuth obligations** such as issuer validation and credential
  binding. Not observable from a server audit.
- **What tools do.** The audit never calls them, so the score judges how tools
  are described and typed, not how they behave. [Smoke mode](/smoke-mode)
  covers that gap for your own server, outside the score.

## Why did my score change?

The score is deterministic for the same server state and the same mcpscore
version. When it moves, one of three things moved:

1. **A different mcpscore version ran.** Most releases add rules, which
   changes both numbers. The report's `mcpscore_version` says which engine
   scored it. Scores compare only within one version, per the
   [stability contract](/stability#evolving-by-design).
2. **The audit type differs.** A partial audit covers far fewer checks. A
   modern-lifecycle server's main score includes readiness points
   (`readiness.counted_in_main`) and a legacy server's does not.
3. **The server answered differently.** A rolling deploy or mixed replica
   versions behind a load balancer make byte-identical probes get different
   answers. A server that rate-limits the probes turns rules into
   `insufficient-data` skips, which changes the maximum. Diff the two JSON
   reports by `rule_id`. The flipping rule is the finding, and it usually
   points at the server's consistency.

## Disagree with a rule?

Open an issue with the `rule_id` and the spec text you believe contradicts
it. Rules are required to be defensible by citation, and a rule that cannot
be defended is a bug. To propose a new rule, see
[CONTRIBUTING](https://github.com/mcp-box/mcpscore/blob/main/CONTRIBUTING.md).
